# LumoAuth Guard for OpenClaw v0.1.0 (`v0.1.0`)

**Release Date:** November 20, 2026  
**Tag:** `v0.1.0` (signed)

## Package

| Package | Registry | Version |
| :--- | :--- | :--- |
| `@lumoauth/openclaw` | npm | `0.1.0` |

The OpenClaw plugin id is `lumoauth`. This release follows version 1 of the [LumoAuth Guard contract](https://github.com/lumoauth/agent-guard), as of `agent-guard` commit `54f19ba`.

This is the first release. LumoAuth Guard checks every tool call that your OpenClaw agent makes, before the tool runs. Each call is allowed, sent to you for approval, or blocked. You keep the rules in LumoAuth, not in the conversation, so a prompt injection cannot change them. The check runs in OpenClaw's own process, outside the model.

---

## Install

```sh
openclaw plugins install npm:@lumoauth/openclaw
openclaw lumoauth setup
```

OpenClaw asks two questions during the install. The first asks whether to install a plugin from npm instead of ClawHub. The second lists what the plugin registers and asks you to accept it. Answer `y` to both. In a script, add `--force --accept-capabilities` to the install command.

Setup asks for your LumoAuth dashboard address and a preset. Then it prints a link, a code and a key fingerprint. Open the link, check that the code and the fingerprint match your terminal, and approve the agent. If an OpenClaw gateway is running, restart it once with `openclaw gateway restart`.

**Requirements:**

- OpenClaw 2026.11.5 or later.
- Node.js 24 or later.
- A LumoAuth organization. The Guard works on every LumoAuth plan. Approvals in the LumoAuth app, Slack and Discord need the Agent Governance add-on.

The package has no runtime dependencies.

## Highlights

### 1. Every Tool Call Is Checked Before It Runs

The Guard runs in OpenClaw's `before_tool_call` hook at priority -1000. It runs after every other plugin, so it checks the arguments that the tool really receives.

- It checks built-in tools, MCP tools and the tools of other plugins.
- A call through `dispatch_action` is checked as the tool that it runs, with that tool's arguments. Tool-search ids such as `openclaw:core:web_fetch` count as the tool that they name. Each call gets one decision and one audit receipt.
- Every tool call is blocked until setup finishes. The Guard fails closed on purpose.

The first step that applies gives the answer:

1. **Locked:** blocked until you run `openclaw lumoauth unlock`.
2. **Not set up:** blocked.
3. **Protected:** blocked, or sent for approval (see [Hard Rules](#2-hard-rules-that-no-setting-removes)).
4. **No confirmation from LumoAuth:** blocked when the agent is suspended, or when LumoAuth cannot confirm the agent's permissions for longer than 5 minutes.
5. **Granted:** the call runs. After untrusted input, a call that sends data out asks you first.
6. **Not granted:** asks you. Set `onUngranted` to `block` to block it instead.

Each tool call maps to one capability:

| Kind of tool | Capability | Example |
| :--- | :--- | :--- |
| Built-in tools | A fixed capability for each tool | `read` is `files:read`, `exec` is `shell:exec`, `message` is `messages:send` |
| MCP tools | `mcp:<server>:<risk>:<tool>` | `mcp:github:read:list_issues`. Grant `mcp:github:read:*` to allow every read-only GitHub tool. |
| Other plugin tools | `tool:<name>` | `tool:weather` |
| `dispatch_action` | The capability of the tool that it runs | A `web_fetch` through `dispatch_action` is checked as `web_fetch`. |

The risk of an MCP tool comes from the tool's name. When a call is blocked, the model receives the reason. When a capability is missing, the message tells the owner which one to add, with a link to the agent's page in LumoAuth.

### 2. Hard Rules That No Setting Removes

No setting, capability or approval removes these rules:

- **The Guard itself:** the agent cannot read the Guard's key or change its files.
- **OpenClaw's configuration:** the agent cannot change OpenClaw's settings or credentials, install or remove plugins, or run `openclaw plugins`, `openclaw config` or `openclaw lumoauth`.
- **Credential stores:** SSH keys, cloud credentials (`~/.aws`, `~/.azure`, `~/.config/gcloud`, `~/.kube`), package registry tokens and browser profiles are blocked.

These calls need your approval every time:

- Reading or writing `.env` files, `*.pem` files and `*.key` files.
- Writing to shell start-up files (`~/.bashrc`, `~/.zshrc`), autostart entries, systemd user units and LaunchAgents.
- Changing the crontab, and creating `at` jobs.

The same path rules apply to every argument of MCP and plugin tools that holds an absolute path or a home path, for example for a filesystem MCP server. File tools may read the skills in OpenClaw's state directory, but never change them.

### 3. Scans of Shell Commands and Code

Before a shell command or a piece of code runs, the Guard scans it for:

- Path tokens, with symbolic links resolved, and protected paths inside strings.
- OpenClaw's admin commands.
- Package changes to OpenClaw or to the Guard.
- Commands that stop OpenClaw.
- Protected environment variables.

A scan is a tripwire, not a sandbox. Use it together with OpenClaw's sandbox (see [Known Limitations](#known-limitations)).

### 4. Extra Care After Untrusted Input

Some tools bring in text that other people wrote: web pages, search results, PDFs, images and messages. After such a tool runs, the session holds untrusted input for 30 minutes.

- During that time, a call that sends data out needs your approval, even when its capability is granted.
- Writing standing instructions to memory needs approval too.
- Creating or changing a skill always needs approval.

### 5. Approvals Where You Are

The `approvals` setting chooses where a person answers:

| Setting | Where you approve |
| :--- | :--- |
| `auto` (default) | Through LumoAuth when the agent may act on your behalf. Otherwise, or when LumoAuth cannot reach you, in OpenClaw. |
| `lumoauth` | Only through LumoAuth. |
| `host` | In OpenClaw: the Control UI and the chat channels that support approvals. |
| `off` | Nowhere: every call that needs approval is blocked. |

**Through LumoAuth:** each request goes to the LumoAuth app on the owner's phone, and to the organization's Slack and Discord approval channels. Only the agent's owner can answer, and the first answer counts. Until you answer, `openclaw lumoauth status` says where you can answer the request. These approvals need the agent's **Can act on behalf of users** switch in LumoAuth.

**In OpenClaw:** you answer **Allow once**, **Allow always** or **Deny**. This works on every LumoAuth plan.

- **Allow always** is offered only for a capability that the agent was not granted. It lasts for the current session and capability, and ends when OpenClaw restarts.
- Calls that touch something protected, and calls after untrusted input, ask every time.

Every request shows the tool, the reason, the capability, the risk and up to five arguments. The values of arguments with names such as password, token, key or cookie are hidden.

### 6. Agent Identity and Enrollment

- Setup creates an EC P-256 key pair on your machine. The private key never leaves it.
- The agent signs in to LumoAuth with `private_key_jwt` and sender-constrained DPoP tokens. There is no shared secret.
- You approve the agent on a LumoAuth page that shows the same code and key fingerprint as your terminal. Setup never needs an admin token.
- The Guard keeps its files in `~/.lumoauth/guard/openclaw/` (mode `0700`, files `0600`). Set `LUMOAUTH_GUARD_HOME` to use another directory.

### 7. Capabilities From LumoAuth

- **`local` mode (default):** the Guard loads the agent's capabilities from LumoAuth every 60 seconds and decides on your machine. This mode works on every plan.
- **`server` mode:** the Guard asks LumoAuth's Ask API about each call.
- When LumoAuth cannot be reached, the last capabilities stay valid for 5 minutes. Then every call is blocked.
- To stop the agent, suspend or delete it in LumoAuth. Every tool call stops within a minute. On the machine, `openclaw lumoauth lock` stops them at once.

### 8. A Record of Every Decision

- Each decision becomes an entry in LumoAuth's audit log. The `after_tool_call` hook completes the entry with the result.
- Argument values never leave your machine. LumoAuth receives a SHA-256 digest of the arguments instead.
- Receipts are sent in batches, with back-off. Receipts that are not delivered before OpenClaw exits are kept on disk and sent on the next start.

### 9. Presets

Setup sends LumoAuth a checklist of capabilities. The preset sets which boxes start ticked, and you can change the ticks on the approval page.

| Preset | Allowed without asking |
| :--- | :--- |
| `observer` | Reading files, web search and pages, memory, sessions, media and skills. The read-only tools of each MCP server. |
| `assistant` (default) | Everything in `observer`, plus writing files and memory, goals and tasks, widgets, and generating media. The read and write tools of each MCP server. |
| `builder` | Everything in `assistant`, plus shell commands, code, background processes, sub-agents and the browser. |

No preset ticks sending messages, scheduled jobs, device control, stored secrets, host administration or skill changes. You grant those on purpose.

### 10. Commands, Doctor and the Skill

| Command | What it does |
| :--- | :--- |
| `openclaw lumoauth setup` | Enrolls the agent. `--yes` asks no questions, `--force` enrolls a new agent in place of the current one. |
| `openclaw lumoauth status` | Shows the agent, its capabilities, the connection to LumoAuth and the latest decisions. |
| `openclaw lumoauth doctor` | Checks the Guard and OpenClaw's security settings: the sandbox, who may message the agent, an exposed gateway, file permissions and plaintext secrets. It changes nothing. |
| `openclaw lumoauth lock [reason]` | Stops every tool call on this machine, at once. |
| `openclaw lumoauth unlock` | Lets tool calls run again. |
| `openclaw lumoauth reset` | Deletes the key and the settings on this machine. |

In a chat, the owner can send `/lumoauth` for a short status and `/lumoauth lock` to stop every tool call. Unlocking works only in a terminal.

The plugin includes the `lumoauth-guard` skill, which tells the model what to do while a person decides on a call, and after a call is blocked.

## Known Limitations

- **The Guard is not a sandbox.** It runs inside OpenClaw's process. An agent that may run shell commands or code runs them as your user. Use the Guard together with OpenClaw's sandbox (`agents.defaults.sandbox.mode`), which `doctor` recommends.
- **Only the tool hook is checked.** The Guard checks the calls that OpenClaw sends through its tool hook. In OpenClaw 2026.11.5, no other path is known.
- **MCP risk comes from tool names.** A malicious MCP server can give a tool a harmless name. Its calls still follow the rules for untrusted input and approvals.
- **Some state is kept in memory.** The untrusted-input window and **Allow always** answers end when OpenClaw restarts.
- **Other plugins run first.** Plugins that run before the Guard can change a call's arguments, and the Guard checks the changed arguments. A plugin that blocks a call ends the check before the Guard runs.
- **Runs with no one to answer cannot show an approval.** Cron jobs, heartbeats and `openclaw agent` from a script get the call blocked instead. Grant the capability in LumoAuth if the run needs it.
- **`openclaw security audit` does not show the Guard's checks.** OpenClaw 2026.11.5 loads plugins there without running them. Use `openclaw lumoauth doctor`.
- **The plugin is not on ClawHub yet.** OpenClaw asks whether to install it from npm, and can show that it cannot verify where the plugin came from.
